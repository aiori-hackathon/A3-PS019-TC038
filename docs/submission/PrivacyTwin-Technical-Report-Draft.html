1. Problem and implemented scope

Structured files and tables can contain candidate personal-data fields with incomplete purpose and retention documentation. A saved human decision can become unreliable after evidence changes. PrivacyTwin inspects synthetic CSV and SQLite data, produces aggregate technical evidence, links explicit declarations, and records classification and metadata reviews with separate dependencies.

The configured classes are Identity, Contact, Location, Official ID and Demographic. PS-019.pdf requests five predefined classes without enumerating them; the team should confirm this taxonomy with the mentor. The tool makes no automatic lawful-basis determination or universal data-flow inference.

2. Architecture and data handling

Next.js presents Sources → Rules → Inventory → Reviews → Metadata → Changes → Results. FastAPI coordinates a modular Python core. SQLite stores versioned detector policies, immutable aggregate snapshots, explicit declarations, human reviews and append-only events. Sources are controlled local copies; the SQLite adapter reads source tables with read-only access.

Within configured limits, each admitted field is scanned in full. Limits are 10 MB per upload, 20,000 rows per table, 100 columns, 25 SQLite tables and 250,000 cells per source. Exact source/table/column keys determine identity. A rename without a mapping creates a new identity. A failed scan preserves committed evidence.

Raw uploaded files remain in the local source-copy directory; they are not included in aggregate evidence exports. Field names, declarations and reviewer text remain visible in evidence packages. Optional Gemini assistance sends selected aggregate evidence to an external provider; the deterministic scanner, challenge, evaluation and verifier require no model API.

3. Detection and evidence

Configurable rules combine header hints, full-value patterns, normalization and structural validation. Aadhaar-shaped values use Verhoeff validation; GSTIN-shaped values use a check digit. Format/checksum matches are candidates and do not establish issuance, ownership or personal/business status. Declared field meaning is explicit owner context.

Within a class and signal group, only the strongest contribution counts, limiting duplicate-rule inflation. Group contributions are weighted and compared to a configured acceptance threshold. Candidate scores, competing interpretations, mixed evidence and unknown states remain visible. These scores are heuristic evidence weights, not calibrated probabilities.

The sensitivity workbench removes selected signal groups or checksum validation using stored aggregates and the snapshot's frozen scoring policy. Removed weights are not redistributed. Rejected-format counts are retained so checksum ablations can be calculated without rereading raw values. Older snapshots require rescanning for complete validation detail.

4. Metadata and ReviewGuard

Field declarations completely override table defaults; missing properties stay gaps. The configurable checklist covers declared purpose, retention duration/unit, start trigger, owner and provenance. A draft preview calculates gaps and affected review scopes without a write. Saving requires the matching preview and current revisions.

Classification reviews depend on candidate evidence, relevant detector revisions and scoring/materiality policies. Metadata reviews depend on explicit declarations and checklist/resolver policies. Reviews reopen only after the corresponding dependency comparison indicates a material change. Reversion never silently reapproves an already reopened decision.

for each exact source / table / column:
    resolve explicit declaration and provenance
    profile values and run configured detectors
    group evidence, calculate candidates and retain uncertainty
    save immutable aggregate snapshot
    for each saved review scope:
        compare original dependencies with current dependencies
        preserve / reopen / mark missing, recording the reason
show missing metadata, require human review, export evidence

A positive field with no predicted class counts as a false negative. Macro F1 averages supported classes. 7. Portable evidence and verification

The evidence ZIP is produced from one database read transaction. It contains the passport, inventory, gaps, history, current configuration, latest evaluation when available, a file manifest and a standalone standard-library Python verifier. The verifier checks SHA-256 file consistency, policy content identifiers, scan/review references and independent aggregate candidate-score replay.

This generated package replayed 22 snapshots across 8 manifest-listed files. Run python verify_evidence.py synthetic-evidence.zip using the included script. Hashes without an external trusted signature do not establish authenticity, correctness of observations or legal validity.

8. Validation, limitations and submission work

Backend and browser suites cover adapters, scoped reviews, stale saves, preview purity, exports, responsive navigation, sensitivity, challenge isolation and package alteration detection. The current test run is recorded separately in VERIFICATION.md to distinguish software regression checks from detection evaluation.

Limits: single-user local deployment; bounded structured input; hand-configured scoring; uncertain person/business linkage; no independent accuracy estimate yet. Optional AI output is explicitly attributed and cannot supply missing owner declarations. The default demo requires no provider availability.
